# Practice items are extractive only, never generated

## Context and Problem Statement

The program makes study cards from books and tests the reader on them. A card that is subtly wrong teaches
the reader something the book never said, and they have no way to know. How are cards made so that a wrong
answer is impossible rather than merely unlikely?

## Decision Drivers

* A study card is trusted by definition: the reader is memorising it.
* A wrong card is worse than no card, and worse still because it is invisible.
* The books are real, bought books; putting words in their author's mouth is the failure to avoid.
* Whether a card is right has to be decidable by a machine, not by the reader's judgement.

## Considered Options

* Extractive only: every answer is a character substring of the chapter it cites
* Generated by a language model, with a human review pass
* Generated, with a model asked to check its own work

## Decision Outcome

Chosen option: **extractive only**, because it is the only option where "is this card right?" is a string
comparison rather than an opinion. A generated card can be checked by a person, but nobody re-reads a deck of
hundreds, and a model checking itself answers the same way it answered the first time.

Every answer key, every quiz option and every rationale quote is verified as an exact character substring of
the chapter it names. A card that fails is dropped, not corrected.

### Consequences

* Good, because a card cannot say something the book does not say, and this is checkable at any time.
* Good, because the check runs in three places independently: the importer when it writes the deck, the app
  when it syncs the deck, and the audit on demand.
* Good, because it needs no model, no network and no key at study time.
* Bad, because the cards are narrower than a good teacher would write. There are no "explain in your own
  words" or synthesis questions, because neither can be verified this way.
* Bad, because a chapter with no marked terms yields poor cards, which forced a fallback that picks the most
  repeated 2- or 3-word term (`packages/ingestion/ingest/cloze.py`).
* Bad, because the verbatim rule is brittle against text normalisation: a changed space, a Markdown mark or a
  Windows line ending breaks a match, so the comparison has to be defined precisely and identically in the
  Python that writes cards and the Rust that reads them.

### Confirmation

`apps/desktop/src-tauri/src/db/deck_sync.rs` verifies every card against its chapter Markdown on sync and
rejects what does not match, including a card whose chapter cannot be read. Vector 3 of
`.agent/skills/audit-system.py` re-checks every answer key and rationale quote across the whole vault.
`.agent/skills/audit-practice.py` holds the importer's cards to the same rules, and a test keeps the
importer's rules and the audit's rules identical.

## More Information

Two review findings tightened this after it was already the rule. LE-06 found quiz options that were true
sentences from the same chapter, so a reader could pick a true statement and be marked wrong; the question
became "which sentence comes next" instead. LE-07 found cloze answers that were not terms, and prompts that
showed the answer elsewhere in the sentence. Both are in `docs/review/2026-09-14-findings.md`.
