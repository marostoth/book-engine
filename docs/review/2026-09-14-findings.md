- [x] Fixed in 825e9e2  |  Severity: Critical  |  Proof: Confirmed in your real data  |  Effort: Small  |  Fix order: step 1

**What happens.** In the desktop app, every answer to a scenario (multiple-choice) card shows as incorrect, and the correct option is never highlighted. **Why.** Rust renames the field to `isCorrect` (`#[serde(rename_all = "camelCase")]` on `ScenarioOption`). The TypeScript type and both components read `is_correct`, which is always undefined. Nothing maps one name to the other.

**Evidence.**

- 61 scenario cards are synced: 21 for Dalton and 40 for Kotler.
- `ScenarioCardView.tsx:42` computes `selectedOption?.is_correct ?? false`, which is always false.
- `lib/api/practiceApi.ts` has no mapping between the two names.

### <a id="le-01"></a>LE-01: The review schedule formula is wrong, so cards come back 3 to 6 times too early

- [x] Fixed in 8c030d4  |  Severity: High  |  Proof: Reproduced by running code  |  Effort: Medium  |  Fix order: step 1

**What happens.** FSRS is the formula that decides when a card comes back. The app uses the factor 19/9. FSRS uses 19/81. Retrievability at t = S is 0.567 instead of 0.9, and each interval is S/9 instead of S. You review far too often, and the retention number in analytics uses the same wrong curve.

**Why.** The constant is wrong in two places. The weights are the first 17 FSRS-5 defaults, but the code calls them FSRS-4.5 and mixes formulas from both versions.

**Evidence.**

- Ran a byte-identical copy of `fsrs.rs`: a new card rated Again/Hard/Good/Easy is due in 0/1/1/2 days. With 19/81 it is 10 min/1/3/16 days.
- Good at every due date: the app gives 1, 2, 4, 9, 20, 40, 78 days (76 days to the 7th review). 19/81 gives 3, 8, 20, 47, 104, 218, 438 days (400 days).
- For stability 100 the app schedules 11 days, not 100. For stability 365 it schedules 41 days, not 365.
- Initial difficulty uses the FSRS-4.5 linear formula with FSRS-5 weights: Easy starts at 6.66 instead of 3.22.
- `next_difficulty` reverts toward w4 instead of D0(4). `fsrs.rs:192-193` computes stability from the new difficulty instead of the old one.
- No learning steps, no maximum interval, and `fsrs.rs:155` truncates i64 to u32.
- The review path is real: `submit_review` calls `schedule_card` (`db/fsrs_store.rs:282`). The existing tests only check inequalities, so they pass with the wrong math.

**Where.**

### <a id="le-04"></a>LE-04: A card you fail waits behind all new cards

- [x] Fixed in cd8fa1a  |  Severity: High  |  Proof: Reproduced by running code  |  Effort: Small  |  Fix order: step 1

**Progress.** Commit cd8fa1a did the main fix: due reviews now come first, then new cards. Not done yet: a separate daily cap for new cards, and separate "due reviews" and "new cards" numbers in the UI.

**What happens.** A card you rate "Again" should come back soon. Instead it comes back only after every new card in the book has been shown. For Kotler that is 200 new cards, about 9 full sessions at the daily target.

**Why.** A new card gets `due` = the moment of first sync. A failed card gets `due` = the moment of the review, which is later. The query sorts by `due ASC` with a limit, so all the old new-card timestamps come first.

**Evidence.**

- `fsrs_store.rs:41` inserts new cards with `due = now` at sync time.
- `fsrs_store.rs:106` selects `due <= now OR reps = 0`, and `:123` orders `due ASC, reps ASC LIMIT ?`.
- A reviewer ran the app's exact SQL on a copy and confirmed the order.
- Your real database has 265 cards, all due now, with 1 review ever made.

**Where.**

- [`apps/desktop/src-tauri/src/db/fsrs_store.rs:41`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/apps/desktop/src-tauri/src/db/fsrs_store.rs#L41)
- [`apps/desktop/src-tauri/src/db/fsrs_store.rs:106`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/apps/desktop/src-tauri/src/db/fsrs_store.rs#L106)

### <a id="le-05"></a>LE-05: Card sync never removes old cards, and changed questions keep old schedules

- [x] Fixed in 5aa9dd5  |  Severity: High  |  Proof: Confirmed in your real data  |  Effort: Medium  |  Fix order: step 1

**What happens.** When a practice deck is generated again, the database keeps every old card. A card ID that now holds a different question keeps the old schedule and review count. Cards removed from the deck stay due forever. Your database already has duplicates and orphans.

**Why.** Sync is an upsert that updates only the text fields and keeps `state`, `stability`, `difficulty`, `due`, and `reps`. There is no `DELETE FROM fsrs_cards` anywhere. Commit 050fe3f added the book ID as a prefix to card IDs, which split old and new rows.

**Evidence.**

- Dalton: 51 rows, 15 with old IDs (for example `card-ch-02-001`) and 36 with the book prefix. 15 prompts are stored twice.
- Wealth of Nations: 14 rows, none with the prefix. None of its 76 current deck cards are synced.
- A reviewer found 35 Kotler card IDs whose text in the database differs from the deck.
- Reproduced on a copy: a replaced card showed the new prompt with stability 15.7, 1 rep, and due in 2 days.

**Where.**

- [`apps/desktop/src-tauri/src/db/fsrs_store.rs:15-17`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/apps/desktop/src-tauri/src/db/fsrs_store.rs#L15-L17)

**How to fix.**

### <a id="le-07"></a>LE-07: Many cloze cards test trivial words or show the answer

- [x] Fixed in fbd6473  |  Severity: Medium  |  Proof: Confirmed in your real data  |  Effort: Medium  |  Fix order: step 4

**What happens.** Some cloze cards blank out function words or bare numbers. Some prompts show the answer elsewhere in the same text. Some prompts show raw HTML. Many chapters have no cloze card at all.

- Chapters without a cloze card: Wealth 27 of 37, Dalton 3 of 7.
- The exact source matches only when whitespace is ignored: Kotler 26, Wealth 13.

**Where.**

- [`packages/ingestion/ingest/salience.py`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/packages/ingestion/ingest/salience.py)

**How to fix.**

- Reject stopword, single-character, and pure-number answers.
- Strip markup from prompts, and reject prompts that contain the answer twice.
- Require at least one card per chapter, and keep exact-byte checks after normalizing line endings.

### <a id="sec-01"></a>SEC-01: Search results show book text as live HTML

- [x] Fixed in 621c864  |  Severity: High  |  Proof: Reproduced by running code  |  Effort: Small  |  Fix order: step 3

**What happens.** The search window inserts each result snippet as HTML. Book text reaches the index without escaping. A book whose text contains `<img src=x onerror=...>` (a hostile file, or an ordinary web-design book with HTML examples) could run a script inside the app when you search a nearby word. Together with SEC-02 and SEC-03, that script could read files and write files outside the vault.

**Why.** `OmniSearchModal.tsx:161` uses `dangerouslySetInnerHTML`. The EPUB converter does not escape text. The indexer stores raw paragraph text, and FTS5 `snippet()` returns it unchanged.

**Evidence.**

- Reproduced in import: `&lt;img src=x onerror=alert(1)&gt;` in an EPUB became a raw `<img src=x onerror=alert(1)>` in the Markdown.
- Reproduced in search: the copied search returned the intact `onerror` markup in a snippet. Not executed in a real WebView.
- Your index today: `<sup>` in 783 rows, `<br>` in 28 rows, and 0 rows with `<img`, `<script`, `<a `, or `onerror`.
- Searching "sup" already produces broken markup: `96<<mark>sup</mark>>29`.

**Where.**

- [`apps/desktop/src/components/OmniSearchModal.tsx:161`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/apps/desktop/src/components/OmniSearchModal.tsx#L161)
- [`apps/desktop/src-tauri/src/db/indexer.rs:94-118`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/apps/desktop/src-tauri/src/db/indexer.rs#L94-L118)
- [`apps/desktop/src-tauri/src/db/indexer.rs:165`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/apps/desktop/src-tauri/src/db/indexer.rs#L165)
- [`packages/ingestion/ingest/epub_parser.py:243-271`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/packages/ingestion/ingest/epub_parser.py#L243-L271)

**How to fix.**

- Build snippets as React elements: use private-use marker characters in `snippet()`, split on them, and render text nodes plus `<mark>`.
- Escape HTML during import, and strip markup before indexing.

**Related:** [SEC-02](#sec-02), [SEC-03](#sec-03), [RD-03](#rd-03)

### <a id="sec-02"></a>SEC-02: No content security policy, and the app window can load any file on disk

- [x] Fixed in aa7372a  |  Severity: High  |  Proof: Confirmed by reading code  |  Effort: Small  |  Fix order: step 3

**What happens.** The app has no CSP, the browser rule that blocks unknown scripts. The asset protocol allows every path (`**`), so page code can load any file on the computer. This turns any HTML injection into a file-reading hole.

**Why.** `tauri.conf.json` sets `"csp": null` and `assetProtocol.scope` to `["**"]`.

**Evidence.**

- The asset protocol is used for book images (`api.ts:203`), so it cannot simply be removed.

**Where.**

- [`apps/desktop/src-tauri/tauri.conf.json:32-36`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/apps/desktop/src-tauri/tauri.conf.json#L32-L36)

**How to fix.**

- Set a strict CSP (scripts only from the app, images from the app and the asset protocol).
- Limit the asset scope to the vault's `books/*/assets` folders, set at runtime once the vault path is known.

**Related:** [SEC-01](#sec-01), [SEC-03](#sec-03)

### <a id="sec-03"></a>SEC-03: File names from the app are joined into paths without checks

- [x] Fixed in da367e0  |  Severity: High  |  Proof: Reproduced by running code  |  Effort: Medium  |  Fix order: step 3

**What happens.** Backend commands build file paths from values the page sends (book ID, notes file name, topic ID). A value with `..` or an absolute path escapes the vault. Page code can call every command. The import CLI has the same hole in `--book-id`.

**Why.** `PathBuf::join` with an absolute path replaces the base path. There is no ID validation and no app permission manifest. Tauri 2.11.5 skips the permission check for app commands from the app's own origin.

**Evidence.**

- Ran Rust `PathBuf::join`: vault + `C:\Windows\win.ini` gives `C:\Windows\win.ini`. With the canonical `\\?\C:\...` vault path, `..\..\x.md` resolves above the notes folder.
- Copied functions wrote or read outside a temp vault through `save_notes` (`..\`, `../`, absolute), `load_chapter`, a topic ID, and a vocabulary book ID.
- `book-ingest --book-id ../../cli-escaped` exited 0 and wrote outside the vault (`pipeline.py:32-33` overrides the sanitized ID).

**Where.**

- [`apps/desktop/src-tauri/src/vault/reader.rs:47`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/apps/desktop/src-tauri/src/vault/reader.rs#L47)
