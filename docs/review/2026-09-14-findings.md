### <a id="le-02"></a>LE-02: The app marks every scenario quiz answer wrong

- [x] Fixed in 825e9e2  |  Severity: Critical  |  Proof: Confirmed in your real data  |  Effort: Small  |  Fix order: step 1

**What happens.** In the desktop app, every answer to a scenario (multiple-choice) card shows as incorrect, and the correct option is never highlighted. The rating is preset to "Again", so the wrong result also goes into the review schedule. The practice drill and the chapter gatekeeper both have this problem. Browser mode looks fine, because its mock data uses the other spelling.

**Why.** Rust renames the field to `isCorrect` (`#[serde(rename_all = "camelCase")]` on `ScenarioOption`). The TypeScript type and both components read `is_correct`, which is always undefined. Nothing maps one name to the other.

**Evidence.**

- Your real cache database stores scenario options with the keys `key`, `text`, `isCorrect`.
- 61 scenario cards are synced: 21 for Dalton and 40 for Kotler.
- `ScenarioCardView.tsx:42` computes `selectedOption?.is_correct ?? false`, which is always false.
- `lib/api/practiceApi.ts` has no mapping between the two names.

**Where.**

### <a id="le-01"></a>LE-01: The review schedule formula is wrong, so cards come back 3 to 6 times too early

- [x] Fixed in 8c030d4  |  Severity: High  |  Proof: Reproduced by running code  |  Effort: Medium  |  Fix order: step 1

**What happens.** FSRS is the formula that decides when a card comes back. The app uses the factor 19/9. FSRS uses 19/81. Retrievability at t = S is 0.567 instead of 0.9, and each interval is S/9 instead of S. You review far too often, and the retention number in analytics uses the same wrong curve.

**Why.** The constant is wrong in two places. The weights are the first 17 FSRS-5 defaults, but the code calls them FSRS-4.5 and mixes formulas from both versions.

**Evidence.**

- Ran a byte-identical copy of `fsrs.rs`: a new card rated Again/Hard/Good/Easy is due in 0/1/1/2 days. With 19/81 it is 10 min/1/3/16 days.

### <a id="le-04"></a>LE-04: A card you fail waits behind all new cards

- [x] Fixed in cd8fa1a  |  Severity: High  |  Proof: Reproduced by running code  |  Effort: Small  |  Fix order: step 1

**Progress.** Commit cd8fa1a did the main fix: due reviews now come first, then new cards. Not done yet: a separate daily cap for new cards, and separate "due reviews" and "new cards" numbers in the UI.

**What happens.** A card you rate "Again" should come back soon. Instead it comes back only after every new card in the book has been shown. For Kotler that is 200 new cards, about 9 full sessions at the daily target.

**Why.** A new card gets `due` = the moment of first sync. A failed card gets `due` = the moment of the review, which is later. The query sorts by `due ASC` with a limit, so all the old new-card timestamps come first.

**Evidence.**

- `fsrs_store.rs:41` inserts new cards with `due = now` at sync time.
- `fsrs_store.rs:106` selects `due <= now OR reps = 0`, and `:123` orders `due ASC, reps ASC LIMIT ?`.
- A reviewer ran the app's exact SQL on a copy and confirmed the order.
- Your real database has 265 cards, all due now, with 1 review ever made.

**Where.**

- [`apps/desktop/src-tauri/src/db/fsrs_store.rs:41`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/apps/desktop/src-tauri/src/db/fsrs_store.rs#L41)
- [`apps/desktop/src-tauri/src/db/fsrs_store.rs:106`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/apps/desktop/src-tauri/src/db/fsrs_store.rs#L106)

**How to fix.**

### <a id="le-05"></a>LE-05: Card sync never removes old cards, and changed questions keep old schedules

- [x] Fixed in 5aa9dd5  |  Severity: High  |  Proof: Confirmed in your real data  |  Effort: Medium  |  Fix order: step 1

**What happens.** When a practice deck is generated again, the database keeps every old card. A card ID that now holds a different question keeps the old schedule and review count. Cards removed from the deck stay due forever. Your database already has duplicates and orphans.

**Why.** Sync is an upsert that updates only the text fields and keeps `state`, `stability`, `difficulty`, `due`, and `reps`. There is no `DELETE FROM fsrs_cards` anywhere. Commit 050fe3f added the book ID as a prefix to card IDs, which split old and new rows.

**Evidence.**

- Dalton: 51 rows, 15 with old IDs (for example `card-ch-02-001`) and 36 with the book prefix. 15 prompts are stored twice.
- Wealth of Nations: 14 rows, none with the prefix. None of its 76 current deck cards are synced.
- A reviewer found 35 Kotler card IDs whose text in the database differs from the deck.
- Reproduced on a copy: a replaced card showed the new prompt with stability 15.7, 1 rep, and due in 2 days.

**Where.**

- [`apps/desktop/src-tauri/src/db/fsrs_store.rs:15-17`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/apps/desktop/src-tauri/src/db/fsrs_store.rs#L15-L17)
- [`apps/desktop/src-tauri/src/db/fsrs_store.rs:34-49`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/apps/desktop/src-tauri/src/db/fsrs_store.rs#L34-L49)

**How to fix.**

- Give cards a content-based identity (a hash of the normalized prompt and answer).

### <a id="le-07"></a>LE-07: Many cloze cards test trivial words or show the answer

- [x] Fixed in fbd6473  |  Severity: Medium  |  Proof: Confirmed in your real data  |  Effort: Medium  |  Fix order: step 4

**How to fix.**

### <a id="ds-14"></a>DS-14: The vault is on one disk and nothing copies it

on the second internal SSD, and a folder under OneDrive. The first real run wrote 154 files and 21.0 MB into each in
2.4 s, and an independent script that hashes the vault itself and each zip entry itself found 0 missing, 0 extra and
0 different. The vault was snapshotted before and after: byte for byte unchanged.

154-file vault, with its newest file from 2026-09-18 08:02 — **35 hours behind**. All 154 were really on disk and
really in the cloud, 0 of them cloud-only stubs. So nothing updated it, which is why the check is about freshness and
not only about presence. One day of reading time, the bookmark, the preferences and two Syntopicon files were in one
place only. Two smaller corrections: git keeps **three** vault files, not two, because TL-08 kept `_ledger.json` on
purpose; and the size is 21,971,738 bytes, which is 21.0 MiB and 22.0 MB.

vault is **220 characters**. A dated folder takes that to **265** under `E:\book-engine-backups` and **286** under

### <a id="si-06"></a>SI-06: The change-detection hash is not stable

- [x] Fixed in `23f6997`  |  Severity: Low  |  Proof: Confirmed by reading code  |  Effort: Small  |  Fix order: step 5

**What happens.** The index skips unchanged chapters by comparing a hash. The function is called `md5_hash`, but it uses Rust's `DefaultHasher`, whose output can change between Rust releases. After a toolchain update, every chapter can re-index. Harmless, but misleading.

**Why.** `DefaultHasher` has no stability guarantee.

**Evidence.**

- `indexer.rs` defines `md5_hash` with `std::collections::hash_map::DefaultHasher`.

**Where.**

- [`apps/desktop/src-tauri/src/db/indexer.rs:208-213`](https://github.com/marostoth/book-engine/blob/050fe3f124461b61ca3dd8b93e9327d07aa5c17e/apps/desktop/src-tauri/src/db/indexer.rs#L208-L213)

**How to fix.**

- Use a stable hash (for example SHA-256 or xxHash) and rename the function.

**Related:** none

**Fixed.** The hash is SHA-256 now (`sha256_of`, `db/indexer.rs`), and the name carries the algorithm on purpose,
so a change to the algorithm cannot leave the name behind.

- **`sha2` cost no download.** It was already in `Cargo.lock`, because tauri's own build uses it. The lock changes
  by **one line**.
- **The repository already knew this rule, and nothing checked that it was kept.** `db/card_identity.rs` writes
  its own FNV-1a for card ids, with a comment saying plainly why `DefaultHasher` will not do and a test that pins
  the ids so a later build keeps them. The index was the one place the rule was not applied.
- **The name was the second half of the fault.** `md5_hash` said one thing and did another for as long as it
  existed. A name that carries an algorithm is a promise a reader relies on without checking.
- **The one-time cost is understood.** Changing the algorithm makes every saved hash stale, so the first run
  after this reads every chapter once. That is the same cost `SEARCH_ROWS_FORM` exists for, and
  [SEC-01](#sec-01) paid it before.

**Tests.** 5 new in `db/content_hash_tests.rs` and 3 in `packages/ingestion/tests/test_stable_hashes.py`. The one
that matters pins the hash to the SHA-256 of "abc" published in FIPS 180-4, a number from outside this
repository, so no future change can pass with the tests still green. **A chapter nobody touched is not read
again, and an edited one is: nothing tested that before**, and it is the whole reason the hash exists. The Python
half is the wider rule: no Rust code may use `DefaultHasher` for a value it writes down, and no function may be
named after an algorithm its body does not use.

**8 of 8 mutations right.** Seven breaks caught, one negative control green. Run 1 read 6 of 8 and **both misses
were real**. One mutation never applied at all, because these files are kept with CRLF and a multi-line anchor
written with `

other was **a gap in the new test itself**: it sliced each function's text starting at `fn`, so `fn md5_hash`
held the word "md5" in its own name and thereby "proved" it used md5. **The test passed on exactly the fault it
was written for.** The body now starts after the opening brace, and a function's own name is no longer proof of
anything.

### <a id="cq-07"></a>CQ-07: The text reader mixes two columns on some pages

- [x] Fixed in b36ce0f  |  Severity: Low  |  Proof: Confirmed in your real data  |  Effort: Medium  |  Fix order: step 4

**Added 2026-09-18**, after CQ-03. It is not part of the review at `050fe3f`.

**What happens.** On a page laid out in two columns, the text reader can read a line of the left column, then a line of the right. A word is then cut in two, and words from the other column land in the middle of it. The reader sees a word that is not a word, such as `consumPREVIEW` where the book says "consumers", and the rest of the word arrives as a paragraph of its own.

CQ-03 joins the two halves of a sentence that a page break, a picture or a figure label cut apart. It cannot join these, and it must not: the halves do not belong together, and joining them would put words in the book that the book never wrote. So `the_words_prove_the_join` refuses them, and the halves stay apart. That is the honest result, not a fix.

**Why.** `pymupdf4llm` gives the blocks of a page in its own order. On a two-column page that order can run across the gap instead of down one column and then the other.

**Evidence.** Measured on 2026-09-18 with the code at `2f2a8be`, on the pages of the real PDFs.

- **Two-column pages: 172 of 769 in Kotler, 6 of 370 in Dalton.** Every part of Kotler that holds a broken place has two-column pages in it.
- **The `PREVIEW` box label lands inside a word in 6 of the 21 pages that have one.** The book puts a `PREVIEW` box at the start of a chapter, and its title is glued into a word of the first paragraph: `consumPREVIEW`, `influPREVIEW`, `marketPREVIEW`, `communiPREVIEW` and `marPREVIEW` twice.
- **8 paragraphs open with a bare word ending.** Read one by one, **5 are real damage from this** and 3 are not: two open with the real word "Less", and one is a numbered entry of the endnotes. The rule that finds them (`WORD_ENDINGS` in `ingest/layout_stitcher.py`) is a guard against a wrong join, not a counter.
- **Dalton has none of these.** 0 glued words and 0 broken paragraph openings.
- **The two hand-written rules in `ingest/layout_stitcher.py` are here because of this**: the long regex for the Emirates story of chapter 1, which is page 25 and is a two-column page, and the `accordin g` repair. Removing either without a general fix would break that page again.

**What is not known.** The full number of glued words cannot be measured here.

- A glued word leaves no broken sentence behind. `customfrom` reads as one word in the middle of a whole sentence, so no rule finds it.
- Telling a glued word from a real one needs a word list, and no spell checker or word list is installed (`spellchecker`, `nltk`, `enchant` and `wordfreq` are all missing). The book's own text is not a word list either: CQ-03 measured `ers` 227 times in the Kotler page text.
- A wider search for small letters running into capitals finds 76 places, but **that is not a damage count**: most are real names, such as `JCPenney` 13 times, `imageBROKER`, `PRNewswire` and the article ids of Reuters links in the endnotes. Only the `PREVIEW` class above is certain.

So the numbers here are a floor. The real count is higher, and nobody can say by how much without a word list.

**Where.**

- [`packages/ingestion/ingest/pdf_parser.py`](https://github.com/marostoth/book-engine/blob/2f2a8be5e6351001b715b8aa399552ed075cf805/packages/ingestion/ingest/pdf_parser.py) - it calls `pymupdf4llm.to_markdown` and takes the order it gives
- [`packages/ingestion/ingest/layout_stitcher.py`](https://github.com/marostoth/book-engine/blob/2f2a8be5e6351001b715b8aa399552ed075cf805/packages/ingestion/ingest/layout_stitcher.py) - the two hand-written rules, and `WORD_ENDINGS`, which refuses a wrong join
- `%APPDATA%` is not involved. The Kotler book is not in the vault (see the note on removed books), so nothing in the vault shows this today.

**How to fix.**

- Read the blocks of a page with their rectangles (`page.get_text("blocks")` gives one for each), and put them in reading order yourself: find the gap down the middle that no block crosses, then take the left column top to bottom, then the right. Give that order to the markdown step in place of the reader's own.
- Keep a heading or a picture that runs across both columns where its top edge puts it.
- Then, and only then, take out the two hand-written rules, and check that page 25 still reads as one story.
- Measure it the same way afterwards: the count of two-column pages, the `PREVIEW` class, and the paragraphs that open with a word ending. The scripts are in the session scratchpad under `cq07`.

**Why it is Low.** What is proven is about a dozen places in one 769-page book, and the import never invents words to cover it: a broken place stays broken and visible rather than being silently joined wrongly. The unproven part could be larger, which is why this is worth its own entry instead of being forgotten.

**Fixed.** `ingest/reading_order.py` puts the spans of every layout box in reading order before the markdown is
written. Inside a box it finds a vertical gap that **neither a span nor a block of the PDF crosses**, with content on
both sides sharing some height, reads everything left of it and then everything right, and looks at each side again in
case it holds a gap of its own. `ingest/pdf_parser.py` calls it in place of `pymupdf4llm.to_markdown`. The whole "why"
is `docs/decisions/0008-a-page-is-read-in-column-order-not-across-the-gap.md`.

**The finding named one shape of the fault; there are two.** It is not really about columns at all. The engine puts two
different things into ONE layout box and then reads them by their top edge, so it reads across the gap between them.

never mentions it: the big first letter of a story sits to the left of its first three lines, so the engine gave it
after them.

| | before | after |
|---|---|---|
| glued `PREVIEW` words | 6 | **2** (pages 485 and 573) |
| paragraphs opening with a bare word ending | 8 | **5** |
| a small run of letters running into capitals | 11 | **7** |
| steps backwards in the alphabet on one index page of Dalton | 19 | **6** |
| letters lost anywhere in either book | - | **0** |

- **Four of the six glued words are gone** (pages 121, 193, 515, 549). The cut words behind them are joined again by
  `ingest/layout_stitcher.py`, which could not reach them before because the label stood between the halves.
- **The three word-ending openings that go are three of the five** the finding counted as real damage. The other three
  of the eight were never damage: two are the word "Less" and one is a numbered endnote.
- **A drop cap now gives the letter the book has.** Page 121 read `Nou've`; it reads `You've`. The `heal_drop_caps`
  repair in `ingest/pdf_sanitizer.py` had been hunting a capital letter in the first 350 characters of the paragraph
  and had put an `N` there - **a letter the book does not hold**. With the real `Y` in place it needs no guess.
- **Not one letter is lost.** On the 12 pages whose text changes at all, every change is the same one, +7 letters: the
  word `CHAPTER` is **kept once** instead of being deleted. `clean_chapter_markdown` deletes `CHAPTER` whenever a
  capitalised word follows it on a line, which is exactly the shape a run-in label makes, so it had been taking a real
  word out of twelve chapters.
- **113 of the 113 Kotler pages where no box moves come out byte for byte the same.**
- Of the 99 boxes that move, **53 are pictures**, whose text the sanitizer strips: all 50 pages where only picture
  boxes moved give an identical book. A four-column strategy table (page 563) and a two-column list of strengths and
  weaknesses (page 645) both come out grouped by column instead of read across.

**Two things this finding's "How to fix" gets wrong.** Its step 1 says to order the blocks of the page; the fault is
inside a single box, one level below that, and ordering raw blocks means writing the headings, pictures, tables and
outline again. Its **step 3 is stale twice over**: the two hand-written rules it says to remove were already removed by
IN-10, and the rules that remain, in `ingest/pdf_sanitizer.py`, are **still needed**. Measured after the fix over 130
pages, the run-in CHAPTER rule still fires 2 times, `heal_drop_caps` rule 2 seventeen times and rule 3 thirty-six
times. One of its rules, rule 1, fires **0 times in 130 pages** and is worth looking at on its own.

**What is still broken.** Two glued words and three word-ending openings are left. This rule only ever looks inside one
box, and the engine also puts two things into two boxes in the wrong order, which it cannot see.

**Two faults of `pymupdf4llm` were found while measuring and are NOT fixed here.** `ParsedDocument.to_markdown` is not
safe to call twice on one parse: on Kotler page 55 every call adds 1,160 letters to the answer, which is why the code
writes the markdown once. And **228 spans of that book sit in two layout boxes at once**, so their words are written

**Guards.** `packages/ingestion/tests/test_a_page_is_read_in_column_order.py` holds **55 tests**. The fault **cannot be

engine put both in the right order on its own. So the rule is proved against the rectangles those real pages have, each
written down with the page it came from, and the words in the tests are ours. **15 mutations**, each run on its own

**The rule was wrong before it was right, and the real books said so.** The first version asked only that no *span*

the PDF in half. The second version took the widest gap, which on the Dalton index stands in front of the page number

**How to fix.**

- Use `str::get`, `char_indices`, or `split_once` instead of byte slicing.
- Enable clippy in CI with `string_slice` and `indexing_slicing` as warnings.

**Related:** [TL-05](#tl-05)

**Fixed.** The 6 style warnings were already **0**, fixed by [TL-05](#tl-05) turning clippy on with `-D warnings`.
What was left were the byte cuts, and the review counted 19 of them; there were **32** by the time this was fixed,
because nothing was stopping new ones. Two of the 32 were real faults, and both were proven by a test before any
code changed.

**A crash.** The option parser checked `rest.chars().nth(2) == Some(')')`, a count of **characters**, then cut
`rest[3..]`, a count of **bytes**. `(①) Twice a month.` panics: `①` is three bytes long and the cut lands inside
it. Rust stops the whole program there, and that panic rolled back the entire deck sync, so one option in a book
that numbers with circled digits, or in any non-Latin script, **lost every card of the run**. `rest.len() > 3` was
the same mistake in the guard. The `A. text` branch had it too.

**A quietly wrong answer.** `l.strip_prefix("<!--").and_then(|s| s.find("citation:"))` searches the text *after*
the `<!--`, and the offset was used on the whole line. Four bytes out: `<!-- citation: ch-01.md#^p-003 -->` named
the chapter `tion: ch-01.md`, so the card pointed at a file in no vault and was dropped. No crash, no message. The
cloze parser a few lines down had the same shape and was right only by luck, because `find` happened to run on the
whole line there; it uses `split_once` now as well.

- **`split_once` and `char_indices` everywhere an offset was carried.** They cut where they found, so there is no
  offset to apply to the wrong string.
- **`string_slice = "warn"` in `Cargo.toml`**, so `npm run check` fails on a new byte cut.
- **21 cuts stay, and every one is deliberate.** In `search_text.rs`, `highlights.rs`, `notes.rs` and
  `indexer.rs`, the position always comes from `find`, `rfind`, or a byte length that code measured itself, which
  are letter boundaries. Each of those seven functions carries `#[expect(clippy::string_slice, reason = "...")]`
  with the proof, and **`expect` rather than `allow`**, so clippy asks for the attribute back once the cut is gone
  and a stale one cannot pile up.
- **`indexing_slicing` is not enabled**, though the finding named it. Measured: **97 sites** across twelve files,
  most of them in tests, where a panic is a failing test. Indexing a `Vec` you just built is a different hazard
  from cutting UTF-8, and no finding in this register has come from it. The number is written into `AGENTS.md` and
  `ARCHITECTURE.md`, so the choice is recorded rather than forgotten.

**Tests.** 3 new in `db/fsrs_parser_tests.rs` and 2 in `tests/test_one_check.py`. All three Rust tests failed
before the fix, the first two with a panic inside `fsrs_parser.rs` itself.

**8 of 8 mutations right.** Seven breaks caught, one negative control green. Run 1 read 7 of 8, and the miss was a
real gap in the new test: it looked for `allow(clippy::string_slice` as one string, and `cargo fmt` breaks a long
attribute over several lines, so the name and the lint are never next to each other. It reads them apart now.
