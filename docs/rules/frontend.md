# Rules for the reader window

Each rule below was written after a real fault in this repository. It names the test that fails when it is broken, and the review finding at its end is the whole story, in `docs/review/2026-09-14-findings.md`.

The window shows one chapter at a time, as a document of the nodes in `readerExtensions.ts`. It never builds chapter HTML as a string, and it never invents a paragraph anchor.

- **Typing:** Strict mode enabled (`noImplicitAny: true`, `strictNullChecks: true`).
- **Editor:** Markdown AST transformations must occur through headless custom nodes.
- **Chapter Documents:** The reader shows a chapter as a document of the nodes in `readerExtensions` (`components/reader/readerExtensions.ts`). `parseChapterMarkdown` (`lib/markdown.ts`) makes it from markdown-it tokens, block by block, and the first node of each block keeps the anchor of the block. Never build chapter HTML as a string. A new kind of block or tag in a chapter file needs a node or a mark there, and a test that shows it in a document that fits the reader's nodes (RD-03).
- **Anchors:** Never write a paragraph anchor that the app does not have. A citation, a topic citation and a vocabulary word keep the anchor of the block of the passage (`citationAnchorAt`, `src/lib/citations.ts`), an empty anchor when the app does not know one, and never a default such as `^p-001` (RD-04) or a number counted from something else, such as the premises of an argument (RD-11). A form with no box for an anchor saves an empty one. `src/lib/citations.test.ts` reads every file of the app and fails on any line that makes an anchor out of its own numbers: `^p-` and then a digit, an interpolation or a join. It used to look for the one spelling `^p-001`, and missed the RD-11 line in a file on its own list.
- **Highlights:** Draw a saved highlight over the chapter as a decoration (`ReaderHighlights`, `components/reader/ReaderHighlights.ts`), never as a mark in the chapter document. `createHighlight` saves the words of a selection from the text of the chapter document (`readerText`, `lib/readerText.ts`), and `highlightRanges` finds them there again with white space not counted. A new inline node that shows text needs that text in `readerText` (RD-02).
- **The Work of One Scroll:** The reader is memoized (`React.memo`), so every handler that the app gives it is made once with `useCallback`. Never build the options of the editor inside a render: TipTap compares them by identity and would give ProseMirror the whole chapter state again (`readerEditorOptions`, `components/reader/readerEditorOptions.ts`). A scroll reports a percent only when the whole number changes (`createProgressTicker`, `src/lib/readerProgress.ts`). `src/lib/readerEditor.test.ts` and `src/lib/readerProgress.test.ts` fail when the reader loses the memo, holds options of its own, counts a percent on its own, or gets a handler that was made during a render (RD-06).
- **One Keyboard Rule for Every Dialog:** A dialog calls `useDialog` (`hooks/useDialog.ts`) and spreads the `panelProps` it hands back on its panel element. That gives it Escape, a focus trap, the focus back on the way out, and `role="dialog"` with `aria-modal` and a name. Never watch `window` for a key inside a dialog: 5 dialogs did, so one Escape closed the notes drawer and the practice window together. A dialog's own keys, such as the lightbox zoom or the practice ratings, go on the panel's `onKeyDown`, because the focus is held inside the panel while it is open. A dialog the reader types into passes `protectTyping`, so the first Escape shows `DiscardNotice` and only the second one throws the words away. Every button needs a name a screen reader can say: words inside it, or `aria-label` when it holds nothing but an icon. `tests/test_dialogs_follow_one_rule.py` fails when a dialog skips the rule, when one watches `window` again, or when any button of the app has no name at all; `hooks/useDialog.test.tsx` and `components/dialogKeyboard.test.tsx` hold the behaviour (RD-07).
- **A Page Key Is the Page's Only While Nothing Else Has the Focus:** A listener on `window` that takes a plain key for the page, such as Space to scroll, acts only while the focus is on the page itself or on the view it belongs to. A focused control keeps every key: a button is pressed by Space, a select picks by letter, and a dialog holds the focus inside itself. A key held with Ctrl, Cmd or Alt belongs to another shortcut. The dip stream once took Space from every button of the app, and Ctrl+K from search. Every shortcut is chosen in `lib/readerShortcuts.ts`, so one key press runs one shortcut; `readerShortcuts.test.ts` and `components/inspectional/DipStream.test.tsx` hold the behaviour (RD-13).
- **Nothing From Outside Is Believed:** `any` is forbidden by the linter (`@typescript-eslint/no-explicit-any`), and `as unknown as T` is the same escape hatch with more words. A backend answer or a `JSON.parse` result is typed `unknown` and checked in `lib/backendShapes.ts`: `bookMetaFrom` refuses a book file and names the field that is wrong, `highlightsFrom` drops one damaged highlight and keeps the rest. Ask only for the fields the app reads, and let the others travel through, or a book from an older import loses its blueprint on the way in. Never read a field because it "might" be there: four such fallbacks read names that no Rust command, no Python import and no vault file ever wrote. Reach the app shell only through `@tauri-apps/api`, never through `window.__TAURI_INTERNALS__`; only `lib/api/clientBase.ts` may name that object, and only to ask whether the code is inside the app. `tests/test_frontend_stays_tidy.py` holds all of it (RD-09).
- **One Place Per Setting, One Context Per Concern:** A saved setting is read through `hooks/useSettings.ts` (`useSettings`, `useBionic`) and the open book through `hooks/useLibrary.ts`, never passed down as props. Bionic Reading used to have two flags, one in `App.tsx` and one in the saved settings, so the button worked and the app forgot it on restart. The value of each context is built with `useMemo` on its own parts: `Reader` is `React.memo` so a scroll leaves the chapter alone (RD-06), and a context value built fresh on each render undoes that with no prop changing and nothing looking wrong. `hooks/useSettings.test.tsx` fails when that `useMemo` is taken away, and `test_frontend_stays_tidy.py` holds the prop counts of `TopNav`, `Reader` and `AppModals` at what they are now: those numbers may go down, never up (RD-09).
- **A Save Never Starts the Next Save:** A saver that waits for a pause in the typing clears its timer when the timer fires, so "a timer is set" means "words are waiting" and nothing else. The clean-up that saves on leaving is keyed on the id of what it saves into, never on an object that a save replaces. The Synthesis tab was keyed on the topic, and every save gives the topic a new object, so each save ran the clean-up, the timer it asked was never cleared, and one sentence wrote the topic file 51 times. The clean-up must still run when the topic changes: a save made later puts the old topic back over the new one. `components/syntopicon/SynthesisTab.test.tsx` counts the writes (RD-12).
- **A Number Not Known Is a Dash, Not a 0:** A number the app does not have shows as `NO_DATA` (`lib/analyticsText.ts`), and so does every number worked out from it. Hold data that has not come as `null`, never as an empty list: an empty list is a real answer, and a streak or a sum worked out from it is a real 0. The analytics window held the review days as `[]` while they loaded and after a failed load, so every opening told the reader "Streak: 0 days". `components/AnalyticsModal.test.tsx` holds a load open, fails one, and checks that a real 0 still shows (AN-03, RD-15).
- **Nothing Positions a Popover for Us:** there is no positioning library. `SelectionMenu` and `FootnotePopover` place themselves with plain React and inline styles. `@floating-ui/react` sat in `package.json` for months, was imported by no file, and three documents credited it with the work those two components do themselves; RD-09 uninstalled it and TL-07 took it out of the documents. Before you reach for one, say why inline styles are not enough, and add it to `apps/desktop/package.json` and to the **Tooling:** line in the same commit.
- **Editor Library:** Keep every `@tiptap/*` package at the same version, 3.30.4 or later, the first version without the `__proto__` hole of `mergeAttributes` (GHSA-cp6q-959q-f8rh, SEC-05). After a change, `cd apps/desktop && npm audit` must find nothing. The reader takes from the starter kit only the parts that a chapter file uses, so `readerExtensions.ts` turns off a new part of a newer kit; `src/lib/readerEditor.test.ts` fails when the reader gets another node, mark or part.
- **A Component Gets a Component Test:** `npm test` runs `vitest run`, and `vite.config.ts` finds every `src/**/*.test.{ts,tsx}` by pattern, so a test file runs the day it is written. It used to name all 30 files on one line, and a file left off it never ran and said nothing, which is worse than no test at all. A test of a plain function goes in `src/lib/` and runs in `node`; a test that draws a component is a `.test.tsx` beside it and starts with `// @vitest-environment jsdom`. Write one whenever the answer is something only a page can give: a control nobody can reach, a button that runs twice, a line no screen reader announces, or book text that becomes an element instead of words (`components/OmniSearchModal.test.tsx`, SEC-01). `tests/test_one_check.py` fails when the runner goes back to a list of files, or when no component has a test at all (TL-03).
